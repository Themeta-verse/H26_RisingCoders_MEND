### Slide 1: Problem Statement & Track 1 Alignment
- **Slide Title**: Beyond CVEs: Solving Silent Transitive Drift with Gemma 4
- **Track**: Track 1: Gemma 4 — Dependency Resilience
- **The Core Problem**:
  - Traditional security tools focus exclusively on known CVE vulnerability databases.
  - Software actually breaks during real maintenance because of **Dependency Friction & Transitive Incompatibilities**: uncoordinated minor/major bumps, manifest version drift between `pyproject.toml` and `requirements.txt`, dead libraries, and breaking transitive peer dependencies.
- **The Solution (MEND)**:
  - An evidence-grounded dependency navigator that extracts deterministic code usage, evaluates resilience friction, uses local **Gemma 4** (`gemma4:e2b-it-q4_K_M`) for bounded architectural migration guidance, and verifies fixes in isolated sandboxes without touching production targets.
- **Key Metrics**:
  - 100% Zero-Cost Local Inference (Ollama)
  - Zero target repository mutation (100% read-only baseline preservation)
  - 18/18 passing automated verification tests

### Slide 2: Real Target Investigation (`LinkWatch`)
- **Slide Title**: Real Codebase Discovery: The LinkWatch Autopsy
- **Target Repository**: `LinkWatch` (CLI uptime checker & HTML status page)
- **Manifest Evidence & Discrepancies Found**:
  1. **Breaking Transitive Incompatibility**:
     - `requirements.txt:4` pins `Jinja2==2.11.3`.
     - Installed runtime environment has `MarkupSafe 3.0.4`.
     - `Jinja2 2.11.3` imports `from markupsafe import soft_unicode`.
     - `MarkupSafe 3.x` completely removed `soft_unicode`.
     - **Observed Failure**: `tests/test_report.py` immediately crashes with `ImportError: cannot import name 'soft_unicode' from 'markupsafe'` (**Baseline: 9 Passed, 1 Failed**).
  2. **Manifest Specification Drift**:
     - `requirements.txt:5`: `pydantic==1.10.13`
     - `pyproject.toml:17`: `pydantic>=2`
     - Direct manifest contradiction causing non-deterministic builds.
  3. **Pydantic V1/V2 Code Collision**:
     - `linkwatch/config.py:11-25` uses Pydantic v1 `@validator` and `class Config`. Installing `pydantic>=2` without migration breaks config loading.
  4. **Zombie & Obsolete Dependencies**:
     - `six` declared in manifests, but 0 imports in codebase (phantom dependency).
     - `nose==1.3.7` declared in `requirements-dev.txt`, broken on Python 3.12 (relies on removed `imp` module); tests actually use `pytest`.
     - `appdirs==1.4.4` unmaintained since 2017 (needs `platformdirs`).

### Slide 6: The Dependency Exit Capsule & Impact
- **Slide Title**: Reusable Governance: The Dependency Exit Capsule & Migration Ledger
- **What is the Capsule?**:
  - A standardized, versioned (`$schema_version: "1.0.0"`), auditable artifact capturing the complete lifecycle of a dependency migration.
- **Migration Integrity Ledger**:
  - Full lifecycle tracking: `OBSERVED → RECOMMENDED → EXECUTED → VERIFIED / FAILED / INCONCLUSIVE`.
  - Tamper-evident cryptographic SHA-256 digest embedded for CI/CD compliance audit trails.
- **Output Formats**:
  1. `dependency_exit_capsule_linkwatch.json`: Complete structured JSON for CI/CD pipelines, compliance audits, and PR automation.
  2. `dependency_exit_capsule_linkwatch.html`: A standalone, zero-dependency executive dashboard suitable for engineering leads and release managers.
- **Why This Matters**:
  - Dependency migrations no longer rely on guesswork or blind bumps.
  - Teams get deterministic evidence, local AI advisory, and empirical test verification in one unified, 100% local, zero-cost tool.
